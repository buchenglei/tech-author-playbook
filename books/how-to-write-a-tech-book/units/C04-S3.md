# 不能留给以后的事

进度紧的时候，「这个以后再验」听起来像管理问题。对技术书来说，它往往是可信度问题。有些验证一旦推迟，后面补不回来，因为错误已经写进了读者的判断依据。

## 交稿前夜的通读，救不了账本

常见安排是：先写完全部章节，交稿前统一核对数字与命令。到那时改动牵一发动全身。更麻烦的是，有些代码早已跑不出当时的输出，只能删掉或改写成「通常」。删改本身又制造新的不实。

## 五项不可委托

| # | 事项 | 为什么不能拖 |
| --- | --- | --- |
| 1 | 代码可运行 | 跑不起来的代码使整章失效 |
| 2 | 数字有来源 | 编造一次，全书可信度归零 |
| 3 | 引用可追溯 | 假引用是读者第一眼能发现的错误 |
| 4 | 未验证项声明 | 不声明等于剥夺读者的判断依据 |
| 5 | 术语一致 | 长文的头号可读性杀手 |

（E-014）

任一未完成，交付状态只能写 `draft`，不能写 `ready`。这不是措辞问题，是状态问题：draft 表示仍有未关闭项。

## 交接包六文件

| 文件 | 人类用它回答什么 |
| --- | --- |
| 00_README.md | 我该从哪看 |
| 01_outline.json | 结构合理吗 |
| 02_glossary.json | 说法统一吗 |
| 03_ledger.csv | 这些话有依据吗 |
| 04_check.json | 哪些还没过 |
| 05_unverified.md | 哪里可能出错 |

`05_unverified.md` 不得为空。一份声称全部验证过的书稿，几乎一定有一项在说谎。若确实全部实测，写明环境与覆盖范围。

G6 门禁核对六文件与 `05_unverified.md` 的最小长度（E-014）。它卡不住内容真假，但能卡住「忘了写未验证声明」。真假要靠人类抽检。

诚实清单会显出缺口。交稿时附「这些没测」，有人会担心难看。不附的代价更大：读者把推断当事实，出问题时无法定位责任。

把日志全文塞进交接包，不写未验证摘要，人类仍不知从哪看。README 要短，05 要具体到节与影响。

读到这里，你应该能：

1. 写出一句可证伪的书稿承诺，并据此给出 scope_in / scope_out
2. 把承诺拆成卷—章—节，每章标出独立产出与现象/机制/代价职责
3. 按断言分级写完一个写作单元并通过门禁，交出可复检的交接包

做不到哪一条，回到对应章节；三条都做不到，说明本书未兑现承诺——请把它记进 05，而不是默认自己没读懂。
