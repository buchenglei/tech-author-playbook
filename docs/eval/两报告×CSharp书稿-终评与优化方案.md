## 4. 书稿对两份报告的验证与证伪

### 4.1 被书稿**证实**的报告结论

1. **「无硬门禁/无体量锁会塌陷」**——对照 `docs/eval` 旧交付（94 页/440 字）与本次（286 页/2127 字），G8+合同是决定性差异。
2. **「可机检项是硬约束时目标函数会漂到过检」**——本次仍见残留形态：额外 35 个「有文件」的块、spec 空 claims、state 快照不实、人确认默示通过。形式完整度依然跑在人工确认前面。
3. **「金样板与门禁矛盾是危险信号」**——真实书稿 G8 绿、金样板 G8 红，信号分裂仍在。
4. **「命名/判定漂移会伤 Agent」**——本次交付被迫「自造布局」（manuscript/workflow 拆分），正是因为工具与交付规范的路径约定不够硬。
5. **「自检类 MUST 会衰减」**——C01 四节 spec 的 claims 空表、预算数字与 outline 不一致，说明 spec 工序在滚动写作中弱化。

### 4.2 被书稿**证伪或降调**的报告结论

| 原结论 | 书稿证据 | 修正 |
| --- | --- | --- |
| R2：「只能约束出合规，约束不出好书」 | 86 节均值 2127，前几章有机制、边界、错误码与判断 | 改为：**无合同/G8 时只能约束出合规；合同+宪法+G8+诚实清单齐全时可以约束出下限很高的书** |

| R1：质量上限全靠模型能力 | 本书的融合评估、偏差裁定、未验证清单，显示**流程产物本身提升了可审性** | 上限仍受限，但流程显著抬高了下限与可复核性 |

## 5. 最终优化方案（待确认后实施）

### 5.1 原则

1. **先对齐信号，再加规则**——示范物、文档、门禁必须说同一件事。
2. **先元检查，再补检查**——`规则声称 ↔ 脚本实现` 一致性测试优先于新增任何 lint。
3. **允许人显式豁免，不允许 Agent 静默跳过**——waiver 文件化。
4. **本次书稿的好实践进仓库**：篇幅偏差裁定、未验证清单、融合评估、合同字段，升格为模板/附录，而不是让下一本再发明。
