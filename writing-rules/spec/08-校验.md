# 第 7 部分 校验

## 7.1 三级校验，职责不重叠

| 级 | 谁做 | 覆盖 | 能否自评通过 |
|---|---|---|---|
| **L0 脚本** | `spec_lint.py` | 可机检项（约四成规则） | 是：以退出码为准 |
| **L1 证据自检** | 你 | 需要理解才能判的项 | 是，但必须附证据 |
| **L2 交接** | 人类 | 读者行为、领域正确性 | **否，禁止由你判定** |

**VER-01**（MUST｜自检｜阻断）：L2 项不得自行标为通过。未做就写"未做"，并进入交接包。这是本规范对你最硬的一条约束：你可以在 L0/L1 上骗过自己，但不许在 L2 上代替读者。

## 7.2 门禁表

| 门 | 阶段 | 命令 | 通过条件 |
|---|---|---|---|
| **G0** | 立项 | `spec_lint.py --gate G0` | 零错误 |
| **G1** | 读者 | `--gate G1` | 假设表齐全、起点清单可自查 |
| **G2** | 结构 | `--gate G2` | schema、无环、三种职能齐备 |
| **G3** | 样章 | `--gate G3 units/C01-S1.md` | 语言零 P0、六位置齐全 |
| **G4** | 实验 | `--gate G4` | 映射无空行、基线有日志 |
| **G5** | 装配 | `--gate G5` | 引用、编号、索引一致 |
| **G6** | 交接 | `--gate G6` | 交接包完整、未验证项已声明 |
| **G7** | 发布 | `--gate G7 --strict` | 十条红线全过 |

**VER-02**（MUST｜自检｜阻断）：门禁不过不得进入下一阶段。**不允许"先写着，最后一起修"**——批量修复会让你同时面对几十条互相牵连的修改，从而倾向局部打补丁。

## 7.3 修复循环上限

**这是 Agent 失控的高发处**：同一条规则反复失败，你会不断打补丁，每次引入两个新问题。

| 情形 | 动作 |
|---|---|
| 首次失败 | 判根因类型（下表），按类型修 |
| 同一规则第 2 次失败 | 换修法，不得重复上次改法 |
| 同一规则第 3 次失败 | **停止修改**，写 `BLOCK` 卡，转 L2 或上报 |
| 修改引入新失败 | 回滚该次修改，记"该修法无效" |

**VER-03**（MUST｜自检｜阻断）：修复前先定根因。四种根因修法完全不同，误判会越改越坏。

| 根因 | 表现 | 正确修法 | 错误修法 |
|---|---|---|---|
| **缺内容** | 判据要求的东西不存在 | 补内容，或改 `scope` | 改措辞绕过判据 |
| **结构错** | 内容有，位置 / 顺序不对 | 移动、拆节、改大纲 | 在原处加过渡句掩盖 |
| **表达错** | 位置对，句子有问题 | 改句 | 加解释性长段 |
| **事实错** | 断言不成立 | 删断言或改来源 | 降级为"可能"以通过检查 |

**最后一行是本书最想拦住的偷懒**：把"会导致 X"改成"通常会 X"，检查通过了，错误留下了。

## 7.4 十条发布红线

任一条不过，不得发布。每条都有判定方式。

| # | 红线 | 判定 |
|---|---|---|
| 1 | 代码块全部来自仓库且执行通过 | 脚本 + CI |
| 2 | 所有数字可回溯台账 | 脚本 |
| 3 | 无台账外引用，无未读资料 | 脚本 |
| 4 | 强断言有边界条件，或标注未验证 | 自检 + 抽检 |
| 5 | 承诺—章节映射无未解释空行 | 自检 |
| 6 | 读者任务测试完成，或明确声明未做 | 交接 |
| 7 | 术语一致率 100% | 脚本 |
| 8 | 禁用词零命中 | 脚本 |
| 9 | 版本相关断言有版本锚与回落 | 自检 + 抽检 |
| 10 | 交叉引用全部有效 | 脚本 |

**为什么只有十条**：红线过多等于没有红线。十条覆盖四类失效——可复现（1/2/9）、可证伪（3/4）、可回查（7/8/10）、真能用（5/6）。

**MUST 有一百多条，红线只有十条，两者不冲突**：MUST 是**单元级门禁**，不过则该节不能冻结；红线是**发布级门禁**，不过则全书不能交付。前者管"这一节算不算写完"，后者管"这本书能不能交出去"。

把一百多条都当发布红线，等于没有红线——没人能同时盯住一百项。只留十条 MUST，单元写作就失去约束，问题会积累到发布前才爆。

**豁免**：工具书型章节可免 5、6，但必须在正文写明"未做读者验证"。**豁免要写在读者能看见的地方，不能只记在内部文件里。**

## 7.5 自检的回答格式

**VER-04**（MUST｜自检｜阻断）：L1 自检必须用下表格式，逐条给证据。禁止"是/否""已检查""符合要求"。

| 规则ID | 判定 | 证据 | 结论 |
|---|---|---|---|
| UNIT-08 | 代价非空 | `C03-S2.md:87` "该结论仅在单机部署成立" | 通过 |
| AUD-02 | 无比较级断言 | 检索"更/优于"，命中 2 处均有 `given` 支撑 | 通过 |
| FMT-03 | 每图有结论 | 图 1 有；图 2 缺 | **不通过** |

**证据的三类合法形式**：命令 + 输出摘要、`文件:行号`、检索式 + 命中列表。"我确认"不是证据。

## 7.7 回归：改一处要重跑多少

影响面不是"那一节"，是依赖闭包。

| 改动类型 | 重跑范围 |
|---|---|
| 改句子 / 措辞 | 该单元 L0 + L1 |
| 改事实 / 数字 | 该单元 + 所有引用该数字的单元 |
| 改术语 | 全书 L0 + 术语一致检查 |
| 改结构（拆并节） | 该章 + 下游 `deps` 闭包 + 交叉引用全量 |
| 改代码 | 所有含该代码块的单元 + CI |

**VER-05**（MUST｜自检｜阻断）：结构变更后重跑全量 L0。结构变更会让编号、引用、索引同时失效，局部检查发现不了。

**VER-06**（SHOULD｜自检｜登记）：每次改动在 `state.json` 记 `{unit, change_type, rerun_scope, result}`。没有这条记录，回归等于没做。
